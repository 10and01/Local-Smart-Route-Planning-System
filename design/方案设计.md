# 美团AI Hackthon - 本地智能路线规划系统方案

## 一、需求拆解

### 1.1 核心用户场景
| 场景 | 用户痛点 | 系统目标 |
|------|---------|---------|
| 周末出游 | 不知道去哪，路线不合理，走回头路 | 自动生成最优游览顺序 |
| 美食探店 | 想吃好但不想排队，时间难协调 | 结合实时排队+营业时间的路线 |
| 时间预算有限 | 景点多时间少，难以取舍 | 基于约束的POI筛选与串联 |
| 个性化差异 | 有人爱拍照，有人重美食，有人带娃 | 按用户画像生成差异化方案 |

### 1.2 功能需求拆解

### 1.3 非功能需求
- **响应速度**：首屏方案 < 3s，动态调整 < 1s
- **可解释性**：每条路线需说明推荐理由
- **可扩展性**：流程节点可插拔，方便Hackthon快速迭代
- **鲁棒性**：POI数据缺失时的降级策略

## 二、可复用流程设计（Pipeline架构）

整个系统抽象为**4个可复用阶段**，用户偏好作为"主循环变量"贯穿每个阶段，而非事后附加的筛选器：

```
                    用户偏好向量 Preference Vector
                           ↓ 贯穿每个阶段
┌─────────────┐    ┌─────────────────────┐    ┌─────────────────────┐    ┌─────────────────────┐
│   Input     │───→│  Intent Understand  │───→│ Preference-Aware    │───→│ Preference-Driven   │
│  Parser     │    │  + Preference Quant │    │    POI Recall       │    │    Route Engine     │
└─────────────┘    └─────────────────────┘    └─────────────────────┘    └─────────────────────┘
   输入解析              意图理解+偏好量化          偏好感知POI召回            偏好驱动路线规划
                                                                             ↓
                                                                    ┌─────────────────────┐
                                                                    │ Preference-Aligned  │
                                                                    │    Explanation      │
                                                                    └─────────────────────┘
                                                                      偏好对齐解释生成
```

### 2.1 各阶段定义

#### Stage 1: Input Parser（输入解析）
```python
class UserRequest:
    raw_query: str                    # 原始输入
    city: str                         # 目标城市
    date: str                         # 日期（影响营业状态）
    start_time: str                   # 开始时间
    end_time: str                     # 结束时间
    budget: Optional[int]             # 预算（元）
    must_visit: List[str]             # 必去点
    avoid: List[str]                  # 不想去
    travelers: str                    # 出行人群（情侣/亲子/独自）
    preferences: List[str]            # 偏好标签
    transport_mode: str               # 交通方式
```
**复用价值**：所有涉及自然语言输入的系统都可复用此解析层。

#### Stage 2: Intent Understand + Preference Quantization（意图理解与偏好量化）
使用LLM进行结构化抽取 + 意图分类，并输出**可计算的偏好权重向量**：
- **出行类型**：休闲游/特种兵打卡/深度体验/亲子娱乐
- **节奏偏好**：紧凑/适中/悠闲 → 影响时间效率权重
- **主题偏好**：美食/拍照/文化/购物/自然 → 转化为 {主题: 权重} 字典
- **人群标签**：情侣/亲子/独自 → 影响POI人群适配得分
- **约束强度**：硬性约束（时间/预算）vs 软性约束（偏好）

**输出**：`UserPreference` 对象，包含主题权重、人群标签、节奏、预算敏感度等，**后续所有阶段直接消费此对象**。

**复用价值**：通用的NLU+偏好量化模块，可服务搜索、推荐等多场景。

#### Stage 3: Preference-Aware POI Recall（偏好感知POI召回）
多路召回融合，**偏好权重直接影响召回排序**：
```
召回通路1：偏好加权向量检索
  query_embedding = encode(用户意图 + 高权重主题*2)
  → 与用户偏好高度相关的POI获得更高相似度分

召回通路2：偏好标签过滤
  按主题权重排序保留 → 高权重主题类目优先，低权重类目缩减
  例：用户偏好{"美食":0.9, "购物":0.1} → 餐饮POI保留20个，购物POI保留5个

召回通路3：人群适配过滤
  情侣用户 → 过滤掉"亲子乐园"类POI
  亲子用户 → 提升"适合儿童"标签POI的排序

召回通路4：热度排序（兜底）

召回通路5：必去点强制纳入
```
**复用价值**：偏好感知的检索召回框架，任何需要个性化排序的场景可复用。

#### Stage 4: Preference-Driven Route Engine（偏好驱动路线规划引擎）
核心算法模块，**用户偏好内嵌在每一步决策中**：
- **时空建模**：POI坐标、营业时间、建议停留时长
- **偏好引导的POI评分**：`POI得分 = 基础质量 × 偏好匹配系数 × 人群适配系数`
- **偏好加权的贪心构造**：每步选择边际价值最高的POI，边际价值公式中的权重由用户偏好决定
- **偏好引导的2-opt优化**：交换子路径时，不仅看路程减少，还看交换后整体偏好匹配度是否提升
- **多方案生成**：同一用户偏好下，通过调整权重生成体验优先/效率优先/均衡三种方案

**关键区别**：旧架构是"先生成路线再筛选"，新架构是"让偏好引导每一步选择"。

**复用价值**：偏好驱动的TSP求解器，可复用于物流、巡检等需要多目标优化的路径规划场景。

#### Stage 5: Preference-Aligned Explanation（偏好对齐解释）
- **非事后解释**：每个POI的推荐理由在规划阶段就已记录（"选中它是因为匹配了用户的X偏好"）
- **解释生成**：LLM基于"用户偏好 + POI匹配原因 + 时间合理性"生成自然语言
- **对比呈现**：方案A vs 方案B的差异直接对应不同权重侧重

**复用价值**：偏好对齐的解释生成模块，可服务任何需要可解释推荐的产品。

#### Stage 6: Output Formatter（输出格式化）
标准化输出结构：
```json
{
  "plans": [
    {
      "plan_id": "plan_1",
      "theme": "美食+拍照休闲游",
      "total_time": "6小时",
      "total_cost": "约350元",
      "pois": [
        {
          "name": "西湖断桥",
          "arrive_time": "09:30",
          "leave_time": "11:00",
          "duration": "90分钟",
          "transport_to_next": "步行15分钟",
          "tips": "上午光线适合拍照"
        }
      ],
      "reasoning": "推荐理由..."
    }
  ]
}
```

### 3.2 核心模块详细设计

#### 模块A：意图理解 + 偏好量化模块（Intent Understanding & Preference Quantization）

**实现方式**：Prompt Engineering + Few-shot示例，LLM输出意图结构 + 偏好权重向量。

```
System Prompt:
你是一位本地出行规划专家。请从用户输入中提取以下信息：

【结构化意图】
- city: 目标城市
- duration: 游玩时长（小时）
- travelers: 出行人群 [独自/情侣/亲子/朋友/家庭]
- pace: 节奏 [紧凑/适中/悠闲]
- budget: 预算级别 [经济/标准/高端]
- constraints: 约束条件（时间/必去点/禁忌等）

【偏好权重向量】（0~1之间，保留2位小数）
- theme_weights: 每个主题的重要性权重
  例：{"美食": 0.85, "拍照": 0.92, "文化": 0.30, "自然": 0.60, "购物": 0.20}
- willingness_to_queue: 是否愿意排队（0~1）
- willingness_to_walk: 是否愿意多走路（0~1）
- price_sensitivity: 价格敏感度（0~1，越高越在意价格）

请输出JSON格式，不要解释。
```

**输出的偏好向量示例**：
```json
{
  "theme_weights": {"美食": 0.85, "拍照": 0.92, "文化": 0.30, "自然": 0.60, "购物": 0.20},
  "willingness_to_queue": 0.30,
  "willingness_to_walk": 0.70,
  "price_sensitivity": 0.40
}
```

**Hackthon简化策略**：使用LLM直接抽取偏好权重，不训练专属模型。偏好向量贯穿后续所有阶段。

#### 模块B：偏好感知POI召回模块（Preference-Aware POI Retrieval）

**数据准备**：
```python
# POI Embedding生成（含标签、人群、主题信息）
poi_text = f"""
名称：{poi.name}
分类：{poi.category}
标签：{', '.join(poi.tags)}
简介：{poi.description}
特色：{poi.highlights}
适合人群：{poi.suitable_for}
"""
poi.embedding = embedding_model.encode(poi_text)
```

**偏好感知的召回流程**：
1. **偏好加权编码**：将用户query + 高权重主题偏好拼接编码
   ```python
   weighted_query = f"{user_query} 重点想{'和'.join([t for t,w in themes.items() if w>0.7])}"
   query_embedding = embedding_model.encode(weighted_query)
   ```
2. 向量数据库（FAISS/Milvus）相似度检索Top-50
3. **偏好标签过滤与重排序**：
   - 按用户theme_weights对POI进行加权评分
   - 高权重主题类目POI多保留，低权重类目缩减
   - 例：`{"美食":0.9, "购物":0.1}` → 餐饮保留20个，购物保留5个
4. **人群适配过滤**：
   - 情侣用户 → 过滤"亲子乐园"，提升"浪漫"标签POI排序
   - 亲子用户 → 提升"适合儿童"标签POI排序
5. 按距离过滤（超过地理范围舍弃）
6. 保留15~20个候选POI（已按偏好匹配度排序）

#### 模块C：偏好驱动路线规划引擎（Preference-Driven Route Engine）【核心难点】

**问题建模**：
这是一个带时间窗、资源约束、**偏好权重**的定向问题（Preference-Aware Orienteering Problem with Time Windows, PA-OPTW）。

**数学模型**：
```
变量：
  x_ij ∈ {0,1}  # 是否从POI i 到 POI j
  t_i           # 到达POI i 的时间
  s_i           # 在POI i 的停留时长
  w_theme       # 用户主题偏好权重向量
  w_pace        # 节奏偏好权重（影响时间效率惩罚强度）

目标函数（最大化）：
  max Σ [score_i · preference_match(i, w_theme) · crowd_match(i)] · visit_i
       - λ(w_pace) · travel_time
       - μ · wait_time

其中：
  preference_match(i, w_theme) = Σ_{tag∈poi_i} w_theme[tag] / Σ w_theme
  crowd_match(i) = 1 if poi_i.suitable_for 包含用户人群 else 0.5
  λ(w_pace) = 1.0 if 紧凑 else 0.6 if 适中 else 0.4  （悠闲用户不那么在意绕路）

约束：
  1. 路线从起点出发，最终回到终点（或开放路线）
  2. 到达时间必须在营业时间内：[open_i, close_i]
  3. 总耗时 ≤ 用户可用时间
  4. 总花费 ≤ 用户预算
  5. 必去点必须包含
  6. 每个POI最多访问一次
```

**求解算法（Hackthon简化版）**：
```python
def preference_driven_plan(candidates, user_pref, constraints):
    """
    偏好驱动的路线规划算法
    核心思想：用户偏好内嵌在每一步决策中，而非事后筛选
    """
    # Step 1: 计算POI间交通耗时矩阵
    travel_matrix = compute_travel_matrix(candidates)
    
    # Step 2: 【偏好注入】为每个POI计算偏好匹配度
    scored_candidates = []
    for poi in candidates:
        base_score = poi.rating / 5.0  # 基础质量
        pref_match = compute_preference_match(poi, user_pref.theme_weights)
        crowd_match = compute_crowd_match(poi, user_pref.traveler_type)
        # 综合预评分 = 基础质量 × 偏好匹配 × 人群适配
        pre_score = base_score * 0.3 + pref_match * 0.5 + crowd_match * 0.2
        scored_candidates.append((poi, pre_score, pref_match))
    
    # 按偏好匹配度排序 — 高匹配的POI优先被选中
    scored_candidates.sort(key=lambda x: x[1], reverse=True)
    
    # Step 3: 【偏好引导贪心】构造初始路线
    route = preference_guided_greedy(
        scored_candidates, 
        travel_matrix, 
        user_pref,      # 偏好权重影响POI选择
        constraints
    )
    
    # Step 4: 【偏好引导2-opt】优化路线
    route = preference_guided_two_opt(
        route, 
        travel_matrix, 
        user_pref       # 优化时兼顾路程减少 + 偏好匹配度提升
    )
    
    # Step 5: 时间可行性检查与调整
    route = adjust_for_time_windows(route, travel_matrix)
    
    # Step 6: 生成多方案（通过调整权重实现不同侧重）
    alternatives = generate_preference_variants(
        scored_candidates,
        user_pref,
        constraints
    )
    
    return alternatives
```

**关键子算法说明**：

| 子算法 | 作用 | 复杂度 |
|--------|------|--------|
| 偏好引导贪心 | 每步选择边际价值最高的POI，价值公式权重由用户偏好决定 | O(n²) |
| 偏好引导2-opt | 交换子路径时兼顾路程减少和偏好匹配度提升 | O(n²) |
| 多方案生成 | 同一偏好下生成体验优先/效率优先/均衡三种方案 | O(3×n²) |
| Insertion Heuristic | 在时间窗内插入新POI | O(n²) |

#### 模块D：偏好对齐解释模块（Preference-Aligned Explanation）

**核心区别**：旧架构是"生成路线后找理由"，新架构是"规划时就记录每个POI被选中的偏好原因"。

**规划阶段的偏好原因记录**：
```python
def record_selection_reason(poi, user_pref, arrive_time):
    """
    在贪心选择POI时，记录为什么选中它
    这些原因后续直接用于解释生成
    """
    reasons = []
    
    # 记录匹配了哪些偏好主题
    matched_themes = []
    for theme, weight in user_pref.theme_weights.items():
        if weight > 0.5 and theme in poi.tags:
            matched_themes.append(theme)
    if matched_themes:
        reasons.append(f"匹配了你的{'和'.join(matched_themes)}偏好")
    
    # 记录人群适配原因
    if user_pref.traveler_type == "情侣" and "浪漫" in poi.tags:
        reasons.append("适合情侣")
    elif user_pref.traveler_type == "亲子" and "儿童" in poi.tags:
        reasons.append("适合带孩子")
    
    # 记录时间合理性
    if arrive_time.hour < 10 and "拍照" in matched_themes:
        reasons.append("上午光线最好，适合拍照")
    elif 11 <= arrive_time.hour <= 13 and poi.category == "餐饮":
        reasons.append("正好饭点")
    
    return reasons
```

### 6.1 偏好驱动的路线规划主算法

```python
def preference_driven_route_plan(candidates, user_pref, constraints):
    """
    偏好驱动的路线规划主函数
    核心思想：用户偏好内嵌在每一步决策中，生成的路线天然匹配用户
    """
    # 1. 计算交通耗时矩阵
    travel_matrix = compute_travel_matrix(candidates)
    
    # 2. 【偏好注入】为每个POI计算偏好匹配度 + 人群适配度
    scored_candidates = []
    for poi in candidates:
        base_score = poi.rating / 5.0
        
        # 计算偏好匹配度（0~1）：POI标签与用户主题权重的加权匹配
        pref_match = compute_preference_match(poi.tags, user_pref.theme_weights)
        
        # 计算人群适配度（0~1）：POI适合人群与用户出行人群的匹配
        crowd_match = compute_crowd_match(poi.suitable_for, user_pref.traveler_type)
        
        # 综合预评分 = 基础质量 × 偏好匹配 × 人群适配
        pre_score = base_score * 0.3 + pref_match * 0.5 + crowd_match * 0.2
        
        scored_candidates.append((poi, pre_score, pref_match))
    
    # 按偏好匹配度排序 — 高匹配的POI优先被考虑
    scored_candidates.sort(key=lambda x: x[1], reverse=True)
    
    # 3. 【偏好引导贪心】构造初始路线
    route = Route()
    remaining = [item[0] for item in scored_candidates]
    current_time = constraints.start_time
    current_location = constraints.start_point
    
    # 优先插入必去点
    for must in constraints.must_visit:
        if must in remaining:
            # ... 插入必去点逻辑（略）
            pass
    
    while remaining and current_time < constraints.end_time:
        best_poi = None
        best_marginal_value = -float('inf')
        
        for poi in remaining:
            travel_time = travel_matrix[(current_location, poi)]
            arrive_time = current_time + travel_time
            
            # 硬性约束检查
            if not is_within_open_hours(poi, arrive_time):
                continue
            finish_time = arrive_time + poi.suggested_duration
            if finish_time > constraints.end_time:
                continue
            if constraints.budget and poi.price:
                spent = sum(p.price for p in route.pois if p.price)
                if spent + poi.price > constraints.budget:
                    continue
            
            # ========== 核心：偏好驱动的POI边际价值计算 ==========
            base_score = poi.rating / 5.0
            pref_match = next(
                (item[2] for item in scored_candidates if item[0] == poi), 0
            )
            
            # 从用户偏好获取动态权重
            weights = user_pref.poi_score_weights  # {"experience":0.4, "time_efficiency":0.3, ...}
            
            poi_value = (
                weights["experience"] * base_score +
                weights["preference_match"] * pref_match +
                weights["cost"] * (1 - poi.price / max(1, constraints.budget or 500))
            )
            
            # 时间效率惩罚（用户节奏偏好决定惩罚强度）
            time_penalty = travel_time * (
                0.5 if user_pref.pace_preference == "悠闲" else 
                1.0 if user_pref.pace_preference == "适中" else 1.5
            )
            
            # 边际价值 = POI价值 - 交通成本
            marginal_value = poi_value * 100 - time_penalty
            
            # 个性化加成
            if user_pref.willingness_to_queue > 0.6 and poi.popularity > 0.8:
                marginal_value += 20  # 用户愿意排队 + 热门POI
            if user_pref.traveler_type == "情侣" and "浪漫" in poi.tags:
                marginal_value += 25  # 情侣 + 浪漫标签
            if user_pref.traveler_type == "亲子" and "儿童" in poi.tags:
                marginal_value += 25  # 亲子 + 儿童友好
            
            if marginal_value > best_marginal_value:
                best_marginal_value = marginal_value
                best_poi = poi
        
        if best_poi is None:
            break
        
        # 插入选中的POI，并记录选择原因（用于后续解释生成）
        travel = travel_matrix[(current_location, best_poi)]
        current_time += travel
        
        selection_reasons = record_selection_reason(best_poi, user_pref, current_time)
        route.add_poi(best_poi, current_time, reasons=selection_reasons)
        
        current_time += best_poi.suggested_duration
        current_location = best_poi
        remaining.remove(best_poi)
    
    # 4. 【偏好引导2-opt】优化路线
    route = preference_guided_two_opt(route, travel_matrix, user_pref)
    
    return route


def generate_preference_variants(candidates, user_pref, constraints):
    """
    基于同一用户偏好，生成3个不同侧重的方案
    每个方案通过调整偏好权重来侧重不同维度
    """
    variants = []
    
    # 方案A：体验优先（侧重偏好匹配 + 高评分）
    pref_a = copy.deepcopy(user_pref)
    pref_a.theme_weights = {k: v * 1.5 for k, v in pref_a.theme_weights.items()}
    pref_a.poi_score_weights["preference_match"] = 0.6
    pref_a.poi_score_weights["time_efficiency"] = 0.15
    route_a = preference_driven_route_plan(candidates, pref_a, constraints)
    route_a.theme = "深度体验"
    route_a.description = f"专注你最感兴趣的{top_theme(pref_a)}，精选高匹配度POI"
    variants.append(route_a)
    
    # 方案B：效率优先（侧重时间 + 路程）
    pref_b = copy.deepcopy(user_pref)
    pref_b.pace_preference = "紧凑"
    pref_b.willingness_to_walk = 0.2
    pref_b.poi_score_weights["time_efficiency"] = 0.55
    pref_b.poi_score_weights["preference_match"] = 0.2
    route_b = preference_driven_route_plan(candidates, pref_b, constraints)
    route_b.theme = "高效省时"
    route_b.description = "在最短时间内打卡最多亮点，适合时间紧张"
    variants.append(route_b)
    
    # 方案C：均衡方案（原始偏好权重）
    route_c = preference_driven_route_plan(candidates, user_pref, constraints)
    route_c.theme = "均衡推荐"
    route_c.description = "兼顾体验、时间和预算的综合最优方案"
    variants.append(route_c)
    
    return variants
```

### 6.2 偏好引导的2-opt路径优化

```python
def preference_guided_two_opt(route, travel_matrix, user_pref):
    """
    标准2-opt只优化路程，这里同时优化偏好匹配度。
    用户偏悠闲 → 允许轻微绕路换取更高偏好匹配
    用户偏紧凑 → 优先路程最短
    """
    improved = True
    while improved:
        improved = False
        for i in range(1, len(route.pois) - 1):
            for j in range(i + 1, len(route.pois)):
                # 标准2-opt：计算路程变化
                old_dist = (
                    travel_matrix[(route.pois[i-1].location, route.pois[i].location)] +
                    travel_matrix[(route.pois[j].location, route.pois[j+1].location)]
                    if j + 1 < len(route.pois) else 0
                )
                new_dist = (
                    travel_matrix[(route.pois[i-1].location, route.pois[j].location)] +
                    travel_matrix[(route.pois[i].location, route.pois[j+1].location)]
                    if j + 1 < len(route.pois) else 0
                )
                distance_delta = new_dist - old_dist
                
                # 新增：计算交换前后的偏好匹配度变化
                old_pref_score = sum(
                    compute_preference_match(p.tags, user_pref.theme_weights)
                    for p in route.pois[i:j+1]
                )
                # 模拟交换
                route.pois[i:j+1] = reversed(route.pois[i:j+1])
                new_pref_score = sum(
                    compute_preference_match(p.tags, user_pref.theme_weights)
                    for p in route.pois[i:j+1]
                )
                route.pois[i:j+1] = reversed(route.pois[i:j+1])  # 恢复
                
                preference_delta = new_pref_score - old_pref_score
                
                # 综合判断是否交换
                # 用户偏悠闲 → 允许轻微绕路（distance_weight低）换取更高偏好匹配
                # 用户偏紧凑 → 优先路程最短（distance_weight高）
                distance_weight = 1.0 if user_pref.pace_preference == "紧凑" else 0.6
                preference_weight = 0.5 if user_pref.pace_preference == "紧凑" else 1.0
                
                total_delta = (
                    distance_weight * distance_delta +
                    preference_weight * (-preference_delta * 1000)
                )
                
                if total_delta < 0:  # 交换后更优
                    route.pois[i:j+1] = reversed(route.pois[i:j+1])
                    improved = True
    
    return route
```

## 七、风险评估与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| POI数据不足 | 召回质量差 | 提前准备100+样本数据，使用LLM生成模拟数据 |

| 时间窗求解复杂 | 性能不足 | 采用启发式而非精确算法，接受近似最优 |
| 演示网络问题 | Demo失败 | 准备离线Mock数据，确保演示可控 |

## 九、总结

本方案采用**偏好驱动的Pipeline架构**，将用户偏好从"事后筛选器"升级为"规划引导器"，核心优势：

1. **偏好内嵌而非外挂**：用户偏好直接参与POI召回排序、贪心选择、2-opt优化的每一步决策，生成的路线天然匹配用户，而非"生成后再找最接近的"
2. **可解释性内建**：每个POI被选中时即记录偏好匹配原因，解释不再是"编理由"，而是"读出原因"
3. **多方案有意义**：三套备选方案（体验优先/效率优先/均衡）来自同一偏好向量的不同权重侧重，差异真实且可解释
4. **模块化**：每个阶段独立开发、独立测试，降低Hackthon协作成本
5. **可落地**：使用启发式算法而非复杂优化，在有限时间内保证效果
6. **可演示**：地图可视化 + 自然语言交互，Demo效果直观

**架构设计的关键洞察**：
> 把"先规划再筛选"改为"让偏好引导规划"，每个POI的选择、排序、取舍都有用户的偏好作为决策依据，生成的路线不是"被选中"的，而是"被设计出来"的。

**Hackthon核心产出**：
- 一套偏好驱动的本地路线规划Pipeline
- 一个可交互的Demo系统
- 一份可复用的技术方案文档
